# X（推特）运营全链路 Skill

版本：v1.2，2026-10-27。维护：汇总人 Muse（账号运营方）。
适用：单个 X 账号的日常运营——选题、写帖、审查、发布、互动、数据复盘与规则迭代。
定版背景：2026-10-12~26 两周发了 80 条原创帖，平均浏览约 7、90% 零互动。复盘结论是流程问题不是运气问题：没有独立审查、选题太杂、配图是复述卡、热点只转述不引用。本 skill 即按复盘结果重建的整套打法，**后续一切以数据为准迭代**（见第 10 节）；**账号安全红线见第 9 节，优先于一切增长目标**。

## 0. 总原则

1. **以数据为准**：每条规则都要能被数据推翻。没有数据支撑的“我觉得”不进流程。
2. **没粉丝基础时，只发对别人有用的东西**：口头吐槽、感想、站队、日常流水没人看、没人互动，一律停发。
3. **内容重心是 AI 热点**：新出的模型、工具、功能——它是什么、有什么作用、能给使用者带来什么。泛日常不占帖位。
4. **热点必须引用原帖**：转发/引用原帖再写自己的理解，不许看完热点自己另写一条脱离原帖的帖子。
5. **写、审分离**：写帖的人和审查人是两个独立角色；审查人同时负责选题与每晚的数据学习总结。

## 1. 流水线总览（每天的固定节奏）

审查人定题（前一晚）→ 起草（4 批短帖 + 新闻早晚场 + GitHub 项目线 + 长文线）→ 基础审（Jev 常规评审）→ **审查人预审**（不过重写，最多 2 轮）→ 发布队列执行 → 晚间数据监控记账 → 审查人复盘：总结数据、形成学习结论、定第二天题目、提出规则修订 → 主助手按修订更新本 skill 并推送 GitHub。

任何一环缺失都要在当日汇报里明说，不许静默跳过。

## 2. 审查人系统（核心）

审查人一人三职：

**① 选题人**：第二天发什么由审查人定，不只是给配额——每个帖位给具体题目，产出 reviewer_plan（JSON），字段至少含：

- `date`、总条数上限、各类型配额、停发清单
- `selected_topics`：逐帖位给 `topic`（题目）、`hook_angle`（第一行钩子方向：具体数字/真实结果/踩坑/直接利害）、`usefulness`（对普通读者具体有什么用，一句话）、`needs_ref`（是否必须带原帖链接，能定先写明）、`image_required`（要哪种证据图）
- `learnings`：当日学习结论（见第 10 节）
- `longform`：长文选题建议 1 个，源自近 7 天数据最好的热点或回复里反复出现的问题

起草线照题目写；只许在预留的“当日热点空位”补当天新热点，且必须符合审查标准。

**② 预审员**：每条稿子发布前，站在普通读者和潜在客户的角度逐条审五件事——有没有用、第一行钩子能不能留住人、能不能引起共鸣、像不像真人、配图配得对不对。量化执行用 Jev 钩子 `references/hook_x_reviewer.json`（verdict + 有用性/钩子/共鸣/真人感/配图五维 0-2 分 + 两个 veto：空泛问句凑互动、热点未引用原帖）。

预审通过线（全部满足）：

| 项 | 门槛 |
|---|---|
| verdict | 通过 |
| verdict confidence | >= 0.6 |
| veto_empty_engagement_bait / veto_unquoted_hotspot | 均 < 0.5 |
| score_usefulness | >= 1.5 |
| score_image_fit | >= 1.5 |
| score_hook_strength | >= 1.5 |
| score_human_voice | >= 1.2 |

不过线 → 按最低分的项改稿（钩子低换第一行、有用性低补读者能照做的一步、配图低换证据图、真人感低补真实细节删口号、触发未引用 veto 改引用原帖），重跑预审，**最多 2 轮**；仍不过转人工待审，不许自动发。每条的预审结果留档，供审查人晚间审计。

**③ 学习者**：每晚用当天完整数据复盘（见第 10 节），并审计预审合规：谁没过审就发了、谁重写几轮、谁被拦下，逐条点名；同时审计账号安全：当日回复/点赞/关注/取关量是否越过第 9.3 节护栏、关注粉丝比、有无异常信号（验证码、限制提示、浏览断崖），越线点名并次日降量。

现行停发清单（2026-10-27 定版，数据翻盘前不恢复）：口头吐槽、互关/互fo、热点转述独立帖（不引用的）、站队帖、无实测的跟风帖。

## 3. 内容格式定版

**标准形态（AI 新闻、工具更新、GitHub 项目都用这个）**：
引用转发原帖 → 上方写自己的总结：**一句话说清这是什么 → 编号分点（1. 具体作用/变了什么；2. 哪个点是真有用；3. 对谁有用、能带来什么）→ 一句自己的理解或真实体感**。真用过才写用过，没用过写影响判断，不许假装用过。

范例结构（开源项目 GEOinflow 的传播帖）：引用原帖，上面编号写清“1. 它把多家 AI 平台的爬虫识别和抓取日志合并统计；2. AI 搜索带来的会话、落地页和转化能一起串起来看；3. 自带 PV/UV、漏斗、热力图，能当自建统计面板用”——每一点都是具体作用，不是感想。

- **短帖**：70-100 字为主（引用帖的分点结构可适当放长），hashtag 1-2 个放文末。
- **独立帖写热点**：仅限有自己实测结果时，且正文必须带原帖链接。
- **长文**：只做教程。先找热点再定题，亲手实跑（跑不通不写），实测结果开头，步骤配真实截图，标题图+步骤图齐全。长文一律人工批准后才发，绝不自动发。

## 4. GitHub 项目线（每日 1 个，AI 相关）

核实硬门，顺序不能乱：**先自己看 → 再提炼观点 → 最后审查人核**。

1. **能跑的必须跑一遍**：clone 下来安装、跑 demo/示例命令/核心功能，留下真实运行截图（作首选配图，优先于 README 图），过程里记下它真实的作用和限制。
2. **跑不了的必须真理解**：需要付费 key、特定硬件、大型服务的，读完 README 后再至少读一个源码文件或官方文档页，弄清它真实解决什么问题、限制是什么。只看 README 开头就写的，换项目。
3. **观点落在对人有用的地方**：文案的编号要点必须回答“普通人/开发者能拿它干哪件具体事”，不抄 README 宣传语，不写“强大、一站式、赋能”这类空话。star 数等数字核对后再写。
4. **发布形态**：项目在 X 上有原帖（作者官宣或靠谱分享者）优先引用转发；没有原帖才自发帖带仓库链接。
5. 汇报与台账必须注明核实方式：实跑（附截图文件名）/ 深读（读了哪些文件）。本线不过常规推文评审，但必须过审查人预审（第 2 节同一套门槛）。

## 5. AI 新闻线（每天早晚两场）

- 源：官方与负责人账号（各家 coding agent / 模型团队负责人）、趋势榜、同类资讯账号。
- 筛选三要素同时满足才转：实质性大新闻（新模型/新功能/重大额度或政策变化/官方重要表态）、热度明显高于该账号日常、与账号定位相关。每场最多 2 条，宁缺毋滥，没大新闻就静默。
- 文案按第 3 节标准形态写；过常规评审 + 审查人预审双门才入队。
- 去重只记真实成功：发布日志确认已发且无错误，才记已引用；状态未知的先对账再重试，禁止盲目重发。

## 6. 配图硬规则

- 每条原创帖入队前备好图并带 image_ids；图必须是**证据型**：实测截图、真实运行输出、热点原帖截图、带关键数字的图表。把正文复述一遍的文字卡判不合格。
- 发布队列执行时：带图条目缺图/损坏/上传未获批，一律保持待发状态，**绝不纯文字降级发布**；发布后必须打开线上帖复查真有媒体，没有按裸发事故处理并点名。
- 长文至少标题图 + 步骤实测图。

## 7. 互动线（每天三场）

- **自家帖评论最优先**（2026-10-27 定版）：每场先处理近 48 小时自家已发帖子底下的新评论，再去外面回复热点。逐条实质回复（接住对方具体说的点，挂在他的评论下面）；逐个看评论者是不是蓝 V——是蓝 V 真人且没关注过的，走主页流程（回复+点赞其第一条帖→再关注），计入当日关注配额；非蓝 V 只回复不关注。来留言的人不回应，评论区冷场等于白发。**但必须分批回**：单个帖子一轮最多回 5 条、24 小时内 ≤10 条，剩下的下一场再回；帖子爆量时只挑最有价值的回，不许短时间全回清（红线见第 9.2/9.3 节）。
- 每场目标 >= 20 条**实质回复**：先看完原帖，2-3 句，有观点或真实实测；禁止 1-10 字水评和套话。
- 热点驱动选帖：当日热帖优先；点赞每场有上限（现行 40），关注全天有上限（现行 50），只关蓝 V 真人、走主页流程（先回复+点赞其第一条帖，再关注），回关同流程计入配额。上限数字以审查人按数据修订的最新版为准。
- 只有真实成功后才记已回复/已赞/已关注。

## 8. 发布门与对账

- 自动发布门（常规评审）：verdict=通过、confidence>=0.6、无 veto>=0.5，且审查人预审通过（第 2 节），两门都过才自动发；任一不过转人工待审。评审后端故障时整场跳过起草并明示，发布门保持 fail-closed。
- 回复不幂等：超时或结果未知时先对账（查发布日志/线上状态）再决定是否重试。
- 正文为空、含“测试/请忽略”字样的条目禁止发布；原帖打不开（404/不可见）的回复/引用标记失败，不降级成独立帖。

## 9. 封号红线与真人化护栏（安全底线，优先于增长目标）

依据：X 官方《平台操纵与垃圾信息政策》《自动化规则》《关注限制》与处罚阶梯说明，及 2026 年多轮真实封号/限流案例复盘（2026-10-27 查证）。

X 的处罚阶梯：帖子标签降权 → 账号只读/功能受限 → 账号锁定（手机/邮箱验证解锁） → 临时停用（首犯常见 24 小时–7 天） → 永久停用；另有不发通知的影子限制（搜索不出现、回复被折叠、推荐流量归零）。执行先由自动系统完成、真人也常被误伤，申诉慢且第一次申诉质量最关键——所以策略是**根本不触发**，不指望申诉兜底。粉丝越少信任分越低，同样的动作小号比大号更容易被判，这块从第一天就守死。

### 9.1 内容红线（发什么会被处理）

- 暴力威胁、美化暴力、恐怖与极端组织内容：可直接永久停用。
- 仇恨言论（针对种族/宗教/性别等受保护特征的定向攻击）、定向骚扰、反复 @ 辱骂、人肉（公开他人电话、住址、证件等隐私信息，快速永封）。
- 冒充他人或机构误导他人；诈骗内容与欺骗性链接（仿冒页、虚假赠品、返利诱导、恶意软件/钓鱼链接）。
- 欺骗性的合成/篡改媒体不加说明地发布；操纵选举等公民流程的内容。
- 垃圾式链接：同一链接反复发、纯链接占账号活动大头、在别人帖子回复里塞无关链接。
- 本账号对应执行（已在禁区里，继续死守）：争议站队与政治话题不碰；邀请码/抽奖/互关永久禁；回复里不带推广链接；一切数字与事实必须有来源、查不到不写。

### 9.2 行为红线（做什么动作会被处理）

- **批量、激进、未经请求的回复/@/私信**（官方原文 bulk, aggressive, unsolicited）：爆帖之后短时间内把评论全回一遍正中这一条——量集中、对象全是陌生人，系统按垃圾回复处理；真实案例里多是先只读受限、再停用。回评论必须分批（见 9.3）。
- **follow churn 与无差别激进关注**：大量关注再大量取关刷粉禁止；官方技术上限 400 个/天只是防滥用天花板不是目标，关注满 5,000 后按关注/粉丝比例再限；批量、自动化的关注/取关明文禁止。
- **自动化互动明文禁止**：自动化点赞、按关键词自动回复、给未关注者自动私信、买粉买赞、互刷互动群（engagement pods）、用承诺涨粉的第三方服务。
- **重复与复制粘贴**：同一文案反复发、多条近似回复、多个账号发相同内容，都按垃圾信息处理。
- **话题劫持**：无关帖子塞热门 hashtag、@ 无关大号蹭流量。
- **环境与登录异常**：短时间异地/新设备登录、同 IP 多账号联动会触发锁定验证；账号要为关联第三方应用的行为负责，来路不明的“涨粉/自动化”应用绝不授权。
- **被举报累积**：短时间被多人举报会进人工复核队列——内容擦边、引战、站队是举报来源，从源头不碰（见 9.1）。

### 9.3 我们的量化护栏（写死；审查人只能收紧，不许放宽到接近官方上限）

- **关注**：全天 ≤50 个（官方天花板 400 的 1/8），分三场、每场 ≤17 个；只关蓝 V 真人、走主页流程（先回复+点赞其第一条帖、最后才关注）；**绝不批量取关**：取关只针对确认的死号/垃圾号，每天 ≤10 个、逐个人工判断；关注/粉丝比 >2.5 时暂停净增关注（只保留回关与自家评论者关注），先做内容再恢复。
- **回复**：每场 ≤20 条、任一小时内 ≤12 条；两条回复之间要有真实浏览停顿，不许秒回连发；**自家帖评论分批回**：单个帖子一轮最多回 5 条、24 小时内 ≤10 条，余量下一场再回；帖子突然爆量（评论 >20）时只挑最有价值的回，不追求全回。
- **点赞**：每场 ≤40 条；同一作者单场 ≤3 条，不许对同一人连点。
- **发帖**：原创全天 ≤6 条、相邻两条间隔 ≥30 分钟；同一链接 24 小时内只发一次；hashtag ≤2 个且必须与正文相关；不 @ 与内容无关的账号。
- **节奏真人化**：每天活动自然分布在三场与发布队列里，不在同一分钟集中爆发；先看帖再互动，像正常用户一样有浏览和停留，不做“只输出不浏览”的纯机器节奏；登录环境固定（同一干净出口、同一浏览器），不频繁换 IP/设备。
- 审查人每晚按本节核对当日实际动作量与关注粉丝比，越线在 learnings 里点名，次日降量。

### 9.4 异常急停与恢复

- 出现任一信号，**全线立即停动**并在当日汇报点名：发帖/回复被拦、频繁弹验证码、账号锁定或受限提示、收到 X 官方通知、浏览量断崖式归零疑似降权。
- 停动期 48 小时起：只浏览，不发帖、不回复、不点赞、不关注；删掉可能触发的近期擦边内容；检查设置里第三方应用授权，解绑不认识的。
- 解锁验证与申诉由账号主人本人操作（助手备好申诉要点：如实说明当时行为、点名承诺停止哪一项，不敷衍、不重复乱投——第一次申诉最关键）。

## 10. 数据与迭代环（本 skill 的更新机制）

- 每晚记账：粉丝/关注变化、当日各类帖子条数、逐条浏览/回复/转推/点赞，写入增长日志。
- 审查人每晚产出 learnings，每条含：数据依据、结论、对次日选题或标准的调整。砍量规则：近 7 天原创平均浏览 < 20 且零互动占比 > 70% 时，次日短帖砍到 4-5 条只留热点引用+实测教程；平均浏览或互动率连续 2 天改善才逐步加量。
- **Skill 更新环**：learnings 里确定要改的规则，审查人标 `skill_update_needed` 并给出拟改原文/新文；主助手据此修订本 skill（版本号 +0.1、更新文末版本记录）、同步到各定时任务正文、推送 GitHub 发布库。**每一轮都这样更新，直到数据达标**（阶段目标：原创平均浏览持续高于 20、零互动占比持续低于 50%）；用户在聊天里定的新规矩同样走这条环，不许只改一处。
- 改规则不改历史数据；结论与数据矛盾时以数据为准，旧结论在版本记录里注明作废原因。

## 11. 禁区

- 邀请码相关内容永久停发（晒码/求码/教程/额度/工具站）。
- 不编造数字、时间、人名、实测经历和跑步等个人数据；没有来源的数字不写。
- 不买粉、不刷量、不群发互关。
